# Real-domain gradient and implementation audit

The pilot's fresh/replay loss scaling matches the manuscript and the current production learner. There is no additional accumulation division on replay and no extra optimizer step. A separate numerical scoring-shape defect was confirmed on the GPU and corrected in a versioned trainer; the old trainer and all evidence are unchanged.

For G fresh rows, response cap T, binary MaxRL advantages A_i, token ratios rho_it, and a selected bank of M exemplars of lengths L_m, the implemented objective is:

```
L_fresh = -(1/(G*T)) sum_i sum_t min(rho_it*A_i, clip(rho_it,.8,1.2)*A_i)
L_replay = -(1/M) sum_m (1/L_m) sum_t log pi(y_mt | prompt, prefix)
L_total = L_fresh + .1*(G-1)/G^2 * L_replay
```

Replay is zero in the MaxRL control. Positive-reward policy samples alone populate an initially empty bank. Counts do not weight the target, even when fresh observation counts are highly imbalanced. EOS contributes a response token; prompt and padding tokens do not. The replay loss is likelihood maximization, not entropy maximization over an explicitly normalized bank distribution.

At G=16 the replay coefficient is **0.005859375**. With microbatch b and K=G/b accumulation calls, the strategy divides each fresh microbatch's row mean by K, yielding the 1/G fresh mean. The production replay path runs once at the accumulation boundary and multiplies its chunk gradients by K before the same strategy division. These mechanical factors cancel. The explicit (G-1)/G and 1/G replay factors remain, as specified in the paper. Fresh and replay gradients are combined before clipping and one optimizer step.

The standalone CPU audit is `ops/audit_real_domains_gradient_scaling_20260921.py`; its output is `var/artifacts/real_domains_pilot_20260921/gradient_scaling_audit_20260921/literal_gradient_report.json`. It compares actual production gradients against an independently written full-batch loss using a tiny autoregressive policy. **All 29 cases pass**, including G=16; microbatch sizes 1, 2, 4, 8 and 16; 0, 1, 3 and 16 bank modes; unequal lengths; mixed/all-success/all-failure groups; both arms; deliberately non-unit importance ratios; active gradient clipping; and three AdamW steps with matching moment states. Maximum absolute pre-clipping gradient error is **1.57e-9**. This establishes objective/accumulation fidelity, not behavior of a 7B GPU model.

Fresh loss uses the fixed response cap; replay uses each exemplar's actual length. Therefore increasing T from 16 to 1024 at otherwise identical tokens reduces the fresh gradient 64-fold without reducing replay. The tiny-policy test measures fresh gradient norms 0.052964 versus 0.000827560, and unchanged replay-only norm 0.00315316. This is an intentional difference between the two reductions, not a double divide. It also means the same raw alpha is not a domain-independent ratio of replay to task gradient. Adam's coordinatewise normalization further prevents interpreting loss-coefficient ratios as parameter-update ratios.

Actual 32-update receipts are summarized in `gradient_scaling_audit_20260921/actual_training_diagnostics.json`, with source hashes. QA has zero mixed-reward groups in either arm, so its fresh gradient vanishes throughout. Coding has 27 mixed groups and five all-failure groups in each arm. Gradient-norm clipping never activates: maximum norms are 0.26546 for QA Re:Max, 0.060514 for coding MaxRL and 0.063021 for coding Re:Max, below the cap of 1.0. A zero current gradient can still produce an Adam momentum update after earlier nonzero gradients; the QA MaxRL arm has no such earlier gradient.

The coding receipts contradict an exact “all one-epoch ratios equal one” claim for this numerical implementation. Six MaxRL updates and eight Re:Max updates report nonzero PPO clipping. Mean logged clipping fractions are 0.00007746 and 0.00012597 (0.00775% and 0.01260%); maxima are 0.00063277 and 0.00109649. Old/new log-probability differences reach [-0.24687,0.25240] and [-0.32631,0.29521]. The behavior scorer uses the full padded group width; the production live scorer trims each microbatch to its actual attention width. The subsequent fixed-weight GPU experiment confirms a scoring-rectangle effect in this BF16/SDPA setup. QA log-probability differences and PPO clipping are exactly zero. The isolated GPU diagnostic `ops/diagnose_real_domains_scoring_shapes_20260921.py` compares full-width versus trimmed behavior scores against live production scores at identical weights with SGD lr=0 and parameter-hash checks. In `diagnosis_code_scoring_shapes_v1/diagnostic/result.json`, the old rectangle differs on644/1263 response tokens (mean absolute logp difference0.00302005, maximum0.159584), while both trimmed behavior variants match live logps exactly. This particular group stays within the PPO clip interval in all variants, so it proves removal of false importance-ratio drift rather than a reduction of clipping in that specific group. No new text is generated and all trainable parameter hashes stay unchanged.

The v2 GPU probe is complete. Independent CPU verification loaded all40,370,176 saved gradient coordinates, checked vector-file and per-vector SHA256 values, and recomputed dot products/norms with blockwise NumPy float64 and `math.fsum`, separately from the probe's Torch reductions. The full-width versus trimmed gradient difference is **3.2261552% relative L2**, with cosine **0.9994819828**. The two trimmed variants have exactly identical live token logps but differ by **0.4785418% relative gradient L2**. This residual backward variation is real in the saved vectors; this check does not identify its hardware/kernel cause. The full-versus-trimmed difference includes residual variation and is not an isolated causal effect estimate.

Several recipe differences must be distinguished from a loss bug:

| Component | Real-domain pilot | Manuscript / successful synthetic recipe |
|---|---|---|
| Adaptation | Rank-16 LoRA on q/k/v/o/gate/up/down, 40,370,176 trainable parameters | Full-parameter optimization |
| Learning rate | Constant 1e-5 | 2e-7 at 0.5B/Falcon; 3B peak1e-7 with cosine decay and warmup |
| Updates | 32-update implementation smoke; prepared larger targets512 QA/116 code | Typically3,072 updates, eight passes |
| Response cap |16 QA/1024 code |Domain/model-dependent8–512 |
| Exemplar admission | First encountered verified response for each new mode | Lexicographically smallest normalized token tuple within its first discovery group; new keys sorted |
| Bank scheduling | Sorted task IDs; monotonic cursor then modulo current bank count | Sorted exact-prompt hashes; cursor reduced modulo bank count at each selection |

The admission/scheduler differences are real and disclosed in the pilot identity, but they are not identical to the paper's deterministic bank implementation. On the observed coding traces, four retained exemplars in each arm differ from the production same-group lexicographic choice (4/21 MaxRL modes and4/19 Re:Max modes); QA differs on0/20. Reapplying the production prompt-hash scheduler to the observed admissions changes29/32 coding selections and26/32 QA selections. These comparisons hold the recorded admissions fixed and do not estimate counterfactual model outcomes. Uniform weighting within whichever bank is selected is correct in both implementations.

The manuscript optimizer table currently states beta2=.95. The E79 and E80-R1 preregistrations, submitted ledgers and launchers explicitly use beta2=.999, like the pilot: see `ops/exp_scaling/launch_e79_falcon1b_aligned_verified_replay.py`, `ops/exp_scaling/launch_e80r1_qwen3b_aligned_verified_replay.py`, and their `var/artifacts/*aligned_verified_replay_jobs.json` ledgers. `ops/train.sh` forwards the launcher overrides. Thus beta2 is a manuscript-versus-submitted-recipe inconsistency for those cohorts, not an established pilot-versus-those-cohorts difference. The default launcher value remains.95; cohorts must be checked individually.

No finding here establishes that changing the recipe would improve the pilot. The versioned corrected trainer is `ops/train_real_domains_pilot_20260921_v2.py` (SHA256`e320611aa612d5f2772fe4b45f8e9bbbbad126a5666090b1f97f277049d00535`). It changes only behavior-scoring width, requires microbatch1 so learner row shuffling cannot change the matching rectangle, and preserves objective/bank/optimizer semantics. Nine CPU regressions pass, including exact input-width/mask checks with a shape-sensitive model, an old-trainer counterexample, microbatch rejection, v1-checkpoint rejection and literal clipped/AdamW gradients. Corrected GPU training and independent numerical integrity gates remain necessary before making claims from new runs. No old artifact was replaced.
