# PointMaze waypoint v1

Status: implemented and locally validated; no GPU training campaign has been
launched.

## Domain contract

The language policy chooses one adjacent prompt-visible free cell per decision.
The action mask excludes walls only. It does not filter by the goal, shortest
path, route identity, or revisit history.

A deterministic hash-bound PD controller receives the chosen cell center and
uses only current point position and velocity. MuJoCo remains authoritative for
collisions, local-edge completion, sparse goal success, and the continuous
trajectory. A successful answer is assigned a semantic identity only when its
trajectory crosses exactly one directed route gate.

Public policy state contains:

- the complete ASCII maze;
- current, previous, and goal cells;
- continuous position and velocity diagnostics;
- remaining waypoint budget;
- the current adjacent legal action subset.

Global labels are A=N, B=E, C=S, and D=W. Only labels corresponding to the
current legal subset enter sampling, SFT normalization, on-policy scoring, or
replay scoring.

## Pilot data

The pilot materializer deterministically constructs:

- 64 training tasks;
- 32 development tasks;
- 64 untouched evaluation tasks;
- three to five separated barrier corridors per task;
- balanced geometry rotations with no task fingerprint overlap.

Every advertised route is executed through the pinned PointMaze runtime before
the row is admitted. Certified programs and canonical keys are stored only in
identity.json, not in model rows.

Materialize the full pilot with:

~~~bash
var/seed_paper_eval/paper310/bin/python \
  ops/make_point_maze_waypoint_pilot_v1_data.py \
  --worker-python var/maze_runtime/venv/bin/python \
  --output-root var/data/point_maze_waypoint_pilot_v1
~~~

A cheap structural/runtime smoke is available through --limit-per-split 1.

## Shared warm start

Training examples include every certified route from training maps and no
development or evaluation routes. Examples are generated by replaying the
route through the same public stepwise worker, so each prompt contains the
state actually produced by MuJoCo.

~~~bash
var/seed_paper_eval/paper310/bin/python \
  ops/materialize_point_maze_waypoint_warmstart_v1.py \
  --data-root var/data/point_maze_waypoint_pilot_v1 \
  --worker-python var/maze_runtime/venv/bin/python \
  --output-root var/data/point_maze_waypoint_warmstart_v1
~~~

The SFT trainer renormalizes each label over its recorded legal subset and uses
inverse route length so every demonstrated route contributes equal total
weight per epoch:

~~~bash
var/seed_paper_eval/paper310/bin/python \
  ops/train_point_maze_waypoint_warmstart_v1.py \
  --model var/models/Qwen2.5-0.5B-Instruct \
  --data-root var/data/point_maze_waypoint_warmstart_v1 \
  --protocol docs/point_maze_waypoint_v1.md \
  --output-model var/models/point_maze_waypoint_warmstart_v1 \
  --output-receipt var/artifacts/point_maze_waypoint_warmstart_v1.json
~~~

Model paths should be replaced with the repository's exact immutable base-model
path.

## Development gate

Before online training, use the runner's --evaluation-only mode on all 32
development maps. A reasonable pilot admission band is:

- at least 24/32 maps have a success among eight samples;
- at least 16/32 maps expose two or more canonical routes among eight;
- no geometry stratum is entirely dead;
- aggregate mean success lies between 0.10 and 0.70.

These are development criteria, not claims about the untouched evaluation set.

## Online mechanism pilot

The online runner implements three arms:

1. grpo
2. verified_first_global_replay_canonical
3. verified_first_delayed_singleton_replay_canonical

The third arm disables verified-mass replay while a prompt-local bank contains
only one route, then enables the unchanged mass-plus-balance replay once a
second route is known. This directly tests whether immediate self-imitation of
the first discovered route caused the force-policy treatment to entrench it.

All arms use the same training and evaluation random-number schedules.
Treatment-only derivatives are the semantic/canonical novelty advantage and
verified replay; the control traverses the same replay forward slots with zero
auxiliary derivative. Replay decisions retain their original dynamic legal
supports.

Example one-pass pilot command:

~~~bash
var/seed_paper_eval/paper310/bin/python \
  ops/train_point_maze_waypoint_pilot_v1.py \
  --arm grpo \
  --seed 88501 \
  --model var/models/point_maze_waypoint_warmstart_v1 \
  --data-root var/data/point_maze_waypoint_pilot_v1 \
  --worker-python var/maze_runtime/venv/bin/python \
  --passes 1 \
  --evaluation-interval 64 \
  --evaluation-prompts 32 \
  --evaluation-split dev \
  --output-model var/models/point_maze_waypoint_pilot_grpo_s88501 \
  --output-receipt var/artifacts/point_maze_waypoint_pilot_grpo_s88501.json \
  --output-metrics var/artifacts/point_maze_waypoint_pilot_grpo_s88501.metrics.jsonl \
  --output-replay var/artifacts/point_maze_waypoint_pilot_grpo_s88501.replay.jsonl
~~~

Run the same seed/model/data for the other two arm names. Each training run
monitors only development maps and writes a fresh, hash-bound checkpoint.

After arm selection and all analysis choices are frozen, evaluate a saved
checkpoint once on the untouched evaluation split:

~~~bash
var/seed_paper_eval/paper310/bin/python \
  ops/train_point_maze_waypoint_pilot_v1.py \
  --arm grpo \
  --seed 88501 \
  --model var/models/point_maze_waypoint_pilot_grpo_s88501 \
  --data-root var/data/point_maze_waypoint_pilot_v1 \
  --worker-python var/maze_runtime/venv/bin/python \
  --evaluation-only \
  --evaluation-prompts 64 \
  --evaluation-split eval \
  --output-receipt var/artifacts/point_maze_waypoint_final_eval_grpo_s88501.json \
  --output-metrics var/artifacts/point_maze_waypoint_final_eval_grpo_s88501.metrics.jsonl \
  --output-replay var/artifacts/point_maze_waypoint_final_eval_grpo_s88501.replay.jsonl
~~~

The evaluation-only run writes no checkpoint. Do not promote this pilot to a
confirmatory result until the development gate, job/source identities, arm
selection, and an independent replay audit are frozen.

## Metrics

The runner reports success probability, pass@8, distinct correct routes@8, and
modes per successful sample, both in aggregate and per map. Training telemetry
also includes task-advantage activity, observed route count, novelty magnitude,
replay-bank support, singleton-mass status, and action-support escapes.
