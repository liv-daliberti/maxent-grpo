# E71: Uniform 384-train / 128-eval scale for Graph coloring and PantryPlan

Registered 2026-07-30, before any E71 job was submitted.

## Motivation

The five ModeBench rows reported in the manuscript do not share a training-set
size. Countdown, Python factors, and MathIR each train on 384 prompts and
evaluate on a fixed 128-prompt split. Graph coloring trains on 192 prompts and
evaluates on 96. PantryPlan trains on a 32-prompt subset of a dataset whose
registered training split is already 384 rows, and evaluates on 128.

That inequality is a confound. PantryPlan in particular reaches its 12 passes
in 384 optimizer updates, so each of its 32 prompts is revisited 12 times under
a bank that never has to generalize across a wide prompt pool. Its observed
support collapse may therefore be a property of heavy repetition rather than of
the objective. E71 removes the confound by putting both non-conforming domains
on the common 384-train / 128-eval design.

## Frozen design

Both domains adopt exactly the shape already used by Countdown, Python factors,
and MathIR:

| Quantity | Value |
| --- | --- |
| Training prompts | 384 |
| Evaluation prompts | 128 (`multi_answer` split) |
| Prompt passes | 12 |
| Optimizer updates | 4,608 |
| Rollouts per prompt | 16 |
| Evaluation cadence | every 96 updates (four per pass, 49 coordinates) |
| Evaluation | greedy `pass@1` plus four deterministic `K=8` replicates |
| Seeds | 43, 44, 45, 46, 47 |
| Arms | `grpo` (compute-matched Dr.GRPO), `verified_first_global_replay_canonical` |
| Cells | 20 (2 domains x 2 arms x 5 seeds) |

All xGRPO coefficients, optimizer settings, learning rate, decoding, and the
information firewall are inherited unchanged from the E70 Stage-A launcher. Only
the training-set size, the derived update/evaluation cadence, and the graph
dataset instance differ.

## Data

- Graph coloring uses `var/data/graph_coloring_modebench_v2`, generated by
  `ops/make_exact_answer_mode_data.py` at `--train-size 384 --eval-size 128
  --seed 0`. Identity, split disjointness, and exhaustive support statistics are
  recorded in that directory's `identity.json`. It supersedes
  `var/data/exact_answer_mode_probe` (192/96), which is retained unmodified.
- PantryPlan uses `var/data/pantry_plan_modebench_v2` unchanged. Its registered
  training split has always contained 384 rows; E71 simply stops subsetting it
  to 32. No PantryPlan data is regenerated, so the v2 data tree hash is
  unchanged and every prior PantryPlan qualification remains valid.

## Source provenance and the code-drift check

E71 freezes the working `src` tree at submission. That tree is not identical to
the E70 Stage-A snapshot, so the difference was audited before submission rather
than assumed away.

- Against the **PantryPlan Stage-B** snapshot
  (`source_hash f0c924c0...`), the current tree is byte-identical in
  `canonical_actions.py`, `pantry_support_action.py`, `actor.py`, `args.py`,
  `learner/grpo.py`, and `learner/run.py`. PantryPlan therefore runs the same
  code in E71 as it did at 32 rows.
- Against the **E70 Stage-A** snapshot (`source_hash 41f0b0b5...`), the current
  tree adds the PantryPlan support-mask feature and generalizes a hardcoded
  three-action / 27-sequence assumption to an arbitrary canonical horizon. Every
  changed path is guarded by `canonical_action_task != "none"`. Graph coloring
  runs with `canonical_action_task=none` and `canonical_graph_actions=0`, so none
  of those branches execute and its effective code path is unchanged from E70.
  The E70 Stage-A snapshot could not have been reused regardless: it predates
  `pantry_support_action.py` and cannot run PantryPlan at all.

The consequence for interpretation: the E71 graph coloring and PantryPlan rows
differ from their E70 predecessors in training-set size, not in objective,
optimizer, decoding, or executed learner path.

## Reporting rule

E71 supersedes the Graph coloring and PantryPlan rows of the E70 surface. The
superseded rows are retained in the repository and are not pooled with E71.
Headline cells are five-seed means at the deepest fixed checkpoint
(passes 0, 3, 6, 9, 12) reached by all five seeds of both arms. No faster seed
is carried forward or averaged alone.

## Prospective interpretation gates

Declared before submission; each is answered by the terminal E71 cohort alone.

1. **Graph coloring direction.** Does xGRPO exceed compute-matched Dr.GRPO on
   terminal `pass@8` and `distinct@8` at 384 training prompts? The E70 192-prompt
   cohort showed `pass@8` .371 -> .969 and `distinct@8` .392 -> 2.504. A
   direction reversal or a collapse of the gap to within seed range is a
   negative result and will be reported as one.
2. **PantryPlan collapse reproduction.** At 32 training prompts, matched Dr.GRPO
   raised `pass@1` .359 -> .547 while `pass@8` fell .900 -> .565 and
   `distinct@8` fell 2.436 -> .618. E71 asks whether that accuracy-up /
   support-down trajectory survives a twelve-fold larger prompt pool. If
   PantryPlan's Dr.GRPO `distinct@8` no longer falls materially from its pass-0
   value, the manuscript's temporal-collapse claim does not hold at this scale
   and will be withdrawn rather than restated from the 32-prompt cohort.
3. **Uniformity.** With all five domains at 384/128, does the support-opening
   direction still hold in every domain? This is descriptive, not confirmatory:
   the four E70 Stage-A rows remain a registered subset of a broader
   eight-environment campaign.

No gate is conditioned on a favorable outcome, and no gate may be revised after
the first E71 evaluation coordinate is written.

## Identity and audit

Submission writes `var/artifacts/e71_scale384_05b_identity.json`, binding the
protocol hash, launcher hash, frozen source and operations snapshot hashes, both
data tree hashes, both ten-row job manifests, and the exact submitted job ids.
Jobs are submitted held, audited while held, and released only as a complete
twenty-cell cohort; any incomplete submission is cancelled.
